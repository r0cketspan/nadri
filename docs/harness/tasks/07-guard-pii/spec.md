## 1. 작업 목표

사용자 질문 원문에서 개인정보를 **규칙(정규식 + 검사 규칙 + 문맥 단어)** 으로 찾아, 형식은 남기고 `*`로 가린 텍스트와 가린 종류 목록을 돌려주는 **순수 함수 하나**를 만든다 [PL §3], [A] ADR-21.

- 이 함수의 결과(가린 텍스트)만 이후 단계(Moderation·분류기·LLM·Tavily·DB·로그·평가)로 간다. 원문은 이 함수를 부른 쪽(08 `input_guard`) 밖으로 나가지 않는다 [A] §3.8, [R NFR-35].
- 재사용처: **08** `input_guard`(입력 검사 ①단계), **24** `eval/anonymize`(평가 전 한 번 더 — 멱등 필요) [PL §3 08·24], [A] §3.7-3).
- 추적: NFR-35, ADR-21, G3 재검토 Q3(주민번호 판정)·Q4(가린 모양), 가정 A27·A29.

### 1.1 넣지 않는 것
| 빠지는 것 | 이유 / 들어오는 작업 |
|---|---|
| 입력 검사 순서 연결(PII → Moderation → 분류기), `meta.masked_types`, `security_events(pii_masked)` 기록 | 08 |
| `chat_messages.pii_types` 저장 | 09 |
| 평가용 익명화(별칭·session_id 제거) | 24 (이 함수만 호출) |
| **답변(출력) 가리기** | 하지 않음 — 관광지 대표 전화가 정답이기 때문. 출력 개인정보는 검증 에이전트 보안 항목이 본다 [A] ADR-21, §13 |
| 주소 가리기 | 하지 않음 — 관광 질문의 정상 입력 [R NFR-35], [SG] §3 |
| 이름 탐지용 NER(자연어 처리 모델) | v1.1 후보 [A] §13 |
| 주민번호 검증번호(마지막 자리) 계산 | 쓰지 않음 — G3 Q3 결정 [A] §15 Q3 |
| 영문 이름, 전각 숫자(`０１０`), 1588 같은 업체 대표번호 | §7 엣지케이스·§11 Q8 |

## 3. 공개 인터페이스 (`nadri/guard/pii.py`)

```python
PiiType = Literal[
    "email",           # 이메일
    "resident_id",     # 주민등록번호·외국인등록번호
    "card",            # 카드번호
    "driver_license",  # 운전면허번호
    "phone",           # 전화번호 (휴대폰·유선·070·080)
    "passport",        # 여권번호
    "account",         # 계좌번호 (문맥 단어 근처일 때만)
    "name",            # 이름 (문맥 패턴일 때만)
]

PII_TYPES: tuple[PiiType, ...]
"""적용 순서 = 종류 목록 정렬 순서. ("email", "resident_id", "card", "driver_license", "phone", "passport", "account", "name")"""

@dataclass(frozen=True)
class MaskResult:
    """개인정보 가리기 결과."""
    text: str               # 가린 텍스트 (가릴 것이 없으면 입력과 똑같은 문자열)
    types: list[PiiType]    # 이번 호출에서 실제로 가린 종류. 중복 없음, PII_TYPES 순서. 없으면 []

def mask_pii(text: str) -> MaskResult:
    """
    사용자 입력에서 개인정보를 찾아 형식은 남기고 `*`로 가린다.

    Args:
        text: 사용자 질문 원문 (입력 길이 상한 1,000자는 호출 쪽에서 이미 검사 — 02 Q1)

    Returns:
        MaskResult(가린 텍스트, 가린 종류 목록)

    부수효과: 없음. 로그를 남기지 않는다(원문·가린 결과 모두). 네트워크·DB·파일 접근 없음.
    """
```

- 종류 이름(영문 소문자)은 그대로 `meta.masked_types[]`, `chat_messages.pii_types`, `security_events.categories`에 들어간다 [A] §3.1·§5.1. 08·09·24는 이 상수를 import해서 쓰고 문자열을 다시 적지 않는다.
- 주민등록번호와 외국인등록번호는 형식이 같아 **종류 하나**(`resident_id`)로 묶는다([SG] §3 표도 한 줄).
- `types`는 "이번 호출에서 새로 가린 것"이다. 이미 가린 텍스트를 다시 넣으면 `[]`(§6). 24는 저장된 `pii_types`를 그대로 쓰고 이 값으로 덮어쓰지 않는다.

내부 함수(이름 고정 — 테스트에서 직접 부름):
```python
def _luhn_ok(digits: str) -> bool:
    """숫자만 든 문자열이 Luhn 검사를 통과하는지. 카드번호 판정용."""

def _valid_birth(yy: str, mm: str, dd: str, gender: str) -> bool:
    """성별 자리로 세기를 정해 YYMMDD가 실제 달력 날짜인지. 1·2·5·6 → 1900년대, 3·4·7·8 → 2000년대."""
```

## 4. 종류별 규칙

공통:
- 숫자는 **ASCII `[0-9]`만** 본다(Python `\d`는 전각·다른 문자권 숫자도 잡으므로 쓰지 않는다).
- 모든 숫자 패턴은 앞뒤가 숫자가 아니어야 한다(`(?<![0-9])`, `(?![0-9])`) — 긴 숫자의 일부를 잘못 가리지 않게.
- 정규식은 모듈 수준에서 한 번만 컴파일한다. 아래 "기준 정규식"은 test.md 표를 통과하는 기준안이며(프로토타입으로 표 전체 확인함, 2026-11-21), 구현자가 고쳐도 **test.md 표가 그대로 통과**해야 한다.
- 가린 모양: "형식 유지 + `*`" (G3 Q4). 구분자(`-` `.` 공백 괄호)는 남기고 숫자·영문자만 `*`로 바꾼다. 예외는 표에 적었다.

| 순서 | 종류 | 찾는 모양 (기준 정규식 요약) | 추가 검사 | 가린 모양 (예) | 근거 |
|---|---|---|---|---|---|
| 1 | `email` | `(?<![A-Za-z0-9._%+-])([A-Za-z0-9._%+-]+)(@[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,})(?![A-Za-z0-9])` | — | 아이디 부분을 **고정 4개 `****`**, `@` 뒤 도메인은 그대로: `hong.gildong@gmail.com` → `****@gmail.com` | [SG] §3, G3 Q4, §11 Q2 |
| 2 | `resident_id` | `(?<![0-9])([0-9]{2})([0-9]{2})([0-9]{2})([- ]?)([1-8])([0-9]{6})(?![0-9])` (앞 6 + 뒤 7, 구분자 `-`·공백·없음) | `_valid_birth` 통과(성별 자리 1~8, 실제 달력 날짜 — 윤년 포함). **검증번호는 보지 않는다** | 숫자 전부 `*`, 구분자 유지: `900101-1234567` → `******-*******`, 붙여 쓰면 `*************` | G3 Q3, [R NFR-35] |

| 7 | `account` | 숫자 묶음 `(?<![0-9-])[0-9]{2,6}(?:-[0-9]{2,6}){1,4}(?![0-9-])` 또는 이어 쓴 `(?<![0-9])[0-9]{10,14}(?![0-9])` | ① 하이픈 뺀 숫자가 **10~14자리** ② 그 숫자의 **앞 20자 또는 뒤 20자 안**(이 단계 시점의 텍스트 기준)에 문맥 단어 `계좌`·`입금`·`송금`·`이체`·`은행` 중 하나 | 숫자만 `*`, 하이픈 유지: `1002-123-456789` → `****-***-******` | [PL §3] "계좌 등 문맥 단어 근처", [R NFR-35]. 10~14자리 범위는 **가정**(은행별 자리 수 원문 미확인), §11 Q6 |
| 8 | `name` | 아래 문맥 패턴 바로 뒤의 **한글 2~4자**. 이름 뒤는 어미·조사(`이에요`·`예요`·`입니다`·`이고`·`이야`·`야`·`이라고`·`라고`·`이요`·`요`) 또는 공백·문장부호·끝이어야 함. 한글 부분은 **가장 짧게** 잡는다(`[가-힣]{2,4}?` — `홍길동이에요`에서 `홍길동`만) | 문맥 패턴(아래) | 이름만 고정 `***`: `제 이름은 홍길동이에요` → `제 이름은 ***이에요` | [PL §3] "제 이름은 ○○○ 류", G3 Q4, §11 Q5 |

**이름 문맥 패턴** (`name`, 앞의 것이 이름 앞에 와야 함):
1. `(제|내|저의|나의)\s*이름은` — "제 이름은", "제이름은", "내 이름은"
2. `이름\s*[:：]` — "이름: 홍길동"
3. `성함은`
4. `예약자\s*(명|이름)\s*(은|는|[:：])`, `예약자\s*[:：]` — "예약자명: 홍길동", "예약자 이름은 홍길동", "예약자: 홍길동"
5. `저는\s*([가-힣]{2,4}?)(이)?라고\s*(합니다|해요|해)` — "저는 홍길동이라고 합니다"

넣지 않는 패턴(오탐 큼): "저는 ○○입니다"(→ "저는 학생입니다"), "예약자 ○○"(→ "예약자 확인 방법"), 조사 없이 "○○의 이름은"(→ "경복궁의 이름은 무슨 뜻이야?").

### 4.1 사용자가 관광지 대표 전화를 질문에 쓰는 경우 (PL "확인 필요" 명시)
- **가린다.** 입력 규칙은 번호가 누구 것인지 구별하지 않는다. 예: `064-123-4567 여기 어디야?` → `064-***-**** 여기 어디야?`, types `["phone"]`.
- 이유: 사용자 본인·지인 번호와 관광지 번호를 규칙으로 구별할 수 없고, 구별하려면 DB 조회가 필요해 순수 함수가 깨진다. 보안 우선 원칙([R] 목표 8).
- 영향: "이 번호 어디야?" 같은 **번호로 관광지 찾기 질문은 답할 수 없다**. 관광지 이름으로 물으면 답변(출력)에는 툴 결과의 대표 전화가 그대로 나온다(출력은 가리지 않음, ADR-21).
- `1588-xxxx`·`1330` 같은 업체·안내 대표번호는 전화 규칙 목록(휴대폰·유선·070·080)에 없어 **가리지 않는다**(§11 Q8).
- [SG] §4.2는 "가리면 안 되는 입력"에 관광지 대표 전화를 적었다 — 상충, §8 참고(사용자 확인 §11 Q1).

## 5. 적용 순서와 겹침 처리

```
mask_pii(text):
  1) types = []
  2) PII_TYPES 순서대로 규칙을 하나씩 적용한다. 각 규칙은 "앞 규칙이 이미 가린 텍스트"에 적용된다
       email → resident_id → card → driver_license → phone(국제 → 국내) → passport → account → name
  3) 규칙이 하나라도 가렸으면 그 종류를 types에 넣는다(중복 없음)
  4) MaskResult(text=최종 텍스트, types=types)
```

- **겹침은 순서로 해결한다.** 가린 자리에는 숫자·영문자가 남지 않으므로(전화의 앞자리 국번만 예외), 뒤 규칙이 같은 자리를 다시 잡지 못한다. 위치 계산·겹침 비교 코드는 만들지 않는다.
- 순서 이유:
  - `email` 먼저: `01012345678@naver.com`의 숫자가 전화로 잡혀 `010********@naver.com`이 되는 것을 막는다 → `****@naver.com`.
  - `resident_id`·`card`·`driver_license`(자리 수·검사로 엄격한 것) → `phone` → `account`(가장 느슨한 숫자 묶음, 문맥 필요) 순으로, 구체적인 규칙이 먼저 자리를 차지한다.
  - `name`은 숫자 규칙과 겹치지 않아 마지막.
- 같은 종류가 여러 번 나오면 모두 가린다(`063-123-4567과 064-123-4567` → 둘 다).
- 검사(생년월일·Luhn·문맥)에 실패한 후보는 **그대로 둔다** — 다음 규칙이 잡을 수 있다(예: Luhn 실패 16자리는 계좌 규칙 10~14자리 범위 밖이라 결국 그대로).

## 6. 멱등성 (24 익명화 재사용)

- `mask_pii(mask_pii(x).text).text == mask_pii(x).text` 가 모든 입력에서 성립해야 한다.
- 두 번째 호출의 `types`는 `[]` (새로 가린 것 없음).
- 성립 이유: 가린 결과에는 숫자·영문자가 없는 `*` 자리만 남는다. 전화의 남은 국번(`010`, `02`, `+82-10`)은 뒤 자리가 `*`라 어떤 규칙에도 맞지 않는다. 이메일 아이디 `****`는 이메일 정규식 글자 집합 밖이다. 이름 `***`는 한글이 아니다.
- 이 성질은 test.md P-IDEM에서 "가려야 하는 입력" 전체로 검사한다.

## 7. 엣지케이스

| 상황 | 동작 |
|---|---|
| 빈 문자열·공백뿐 | 그대로, `types=[]` |
| 줄바꿈·여러 칸 공백 | 그대로 보존(가린 자리만 바뀜) |
| 관광지 대표 전화를 질문에 씀 | **가림** (§4.1) |
| `1588-1234`, `1330`, `050x` 안심번호 | 가리지 않음 (§11 Q8) |
| 주소 속 번지 `1100로 2070-61`, 우편번호 `03045` | 가리지 않음 |
| 날짜 `2025-11-21`, `2025.11.21`, `20251121`, 시간 `09:00~18:00` | 가리지 않음 (전화 앞자리·자리 수에 안 맞음) |
| contentid(보통 6~7자리), 요금 `15000원`·`3,000원` | 가리지 않음 |
| 13자리 숫자인데 날짜가 아님(`1234567890123`) | 가리지 않음(월 34) |
| 생년월일은 맞지만 성별 자리 9·0(1800년대) | 가리지 않음 (G3 Q3 "1~8") |
| 2월 29일 | 윤년이면 가림(`000229-3…`), 아니면 그대로(`010229-3…`) |
| 미래 생년월일(예: `991231-3…` → 2099년) | 달력상 유효하면 **가림** — 오탐보다 누락이 더 위험 |
| Luhn 실패 16자리 | 가리지 않음 |
| `은행나무 축제 2025-11-01` (문맥 단어 `은행` 포함) | 날짜는 8자리라 계좌 범위 밖 → 그대로 |
| 문맥 단어 없는 계좌번호 `1002-123-456789` 단독 | **가리지 않음**(알려진 한계, A27과 맞바꿈) |
| `제 이름은 비밀이에요` | `비밀`이 `***`로 가려짐(이름 문맥 안의 과잉 가림 — 무해) |
| 이름이 `이`·`야`로 끝나 어미와 겹침(`김민이에요`) | 가장 짧게 잡아 `김민`만 가릴 수 있음(`***이에요`) — 허용 |
| 영문 이름(`제 이름은 John이에요`) | 가리지 않음(한글 2~4자만) — 알려진 한계 |
| 전각 숫자 `０１０-１２３４-５６７８` | 가리지 않음 — 알려진 한계(한국어 키보드 입력에서 드묾). 정규화(NFKC)는 사용자 텍스트 다른 글자까지 바꿔서 하지 않음 |
| 조합형(NFD) 한글 | 이름 패턴 실패 가능 — 알려진 한계(브라우저 입력은 보통 완성형) |
| URL 속 번호 `?tel=010-1234-5678` | 가림 |
| 1,000자 입력 | 100ms 안(모든 반복이 유한 범위라 되돌아가기 폭주 없음) |
| 입력이 `str`이 아님 | 처리하지 않음(호출 쪽이 pydantic으로 보장) |
